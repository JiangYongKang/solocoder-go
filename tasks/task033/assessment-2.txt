产物不满意：
1. serverStream 的 RecvMsg 方法从 recvCh 读取消息时使用了空白标识符接收，msg 参数未被填充任何数据，任何通过 Stream 接口调用 RecvMsg 都无法获取到实际的流数据。应将 recvCh 读出的值赋值给 msg 参数指向的变量，确保调用方能收到数据。
2. NewStream 方法在应用 ConnectionTimeout 时调用 context.WithTimeout 创建了派生 context，但 cancel 函数被赋值给空白标识符从未调用。如果流在超时到达前就关闭了，context 内部的清理 goroutine 将一直驻留到自然过期才会释放。应将 cancel 保存在 stream.Close 中调用。
3. serverStream 的 Send 方法在 grpcsvc.go 第 834 行实际从 sendCh 读取消息，语义是"接收服务端发来的消息"，但方法名 Send 给人的直觉是"向服务端发送消息"。SendMsg 向 sendCh 写入数据而 Send 从 sendCh 读取，两个命名方向相反的 API 在同一个 Stream 接口中共存，调用方在双向流场景下极易误用。应将两个方向的方法通过命名明确区分，例如将 Send 更名为 Receive 以避免混淆。
4. Invoke 方法和 HandleStream 中都存在双层 goroutine 嵌套设计：外层 goroutine 内部再启动内层 goroutine 执行 handler。每调用一次 RPC 就启动两个 goroutine，大量并发时增加了调度压力和内存开销。可以用单层 goroutine 加 select 多路复用完成超时轮询和 handler 执行。
