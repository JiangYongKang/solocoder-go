产物不满意：
1. raftlog.go 的 run 方法中 applyCommitted 在独立 goroutine 中无锁调用，而 propose 方法在 Leader 处理请求时也在持锁下调用 applyCommitted。两条协程同时对 stateMachine 进行 Apply 操作形成并发数据竞争，破坏了状态机的线性一致性。根因是 applyCommitted 未受互斥锁保护，应将 Apply 操作统一在锁保护下串行执行。
2. raftlog.go 的 updateCommitIndex 方法在集群处于 JointConfig 状态时直接 return 不推进提交索引。提示词要求成员变更期间集群可正常处理客户端请求，但当前实现在联合共识期间所有普通日志条目的提交被阻塞，客户端请求能写入日志却永远无法被标记为已提交，表现为"变更期间写入暂停"。根因是未区分配置条目和普通条目的提交逻辑，应在联合共识期间允许继续提交已复制到多数节点的普通日志条目。
3. raftlog.go 的快照实现中 Snapshot 的 Data 字段是 int 类型仅存储计数，ApplySnapshot 将其转换为 stateMachine.count。快照安装后状态机只恢复了计数而丢失了所有其他状态信息。提示词要求快照包含状态机在某个索引处的完整状态，但当前快照数据不完整无法真正恢复状态。应序列化完整的状态机状态而非仅传递计数器值。
4. raftlog_test.go 中 TestAddNode 和 TestRemoveNode 因 NodeCount 检查失败后，模型修改断言逻辑使测试验证的是配置变更"已启动"而非"已完成"。这种放宽掩盖了联合共识第二阶段可能存在的缺陷，如果第二阶段未正确完成测试仍会通过。提示词要求集群运行时动态添加或移除节点，应验证变更完成后新节点真正加入集群。
5. raftlog.go 中定义了 ErrNoLeader、ErrNodeExists、ErrNotInitialized、ErrNotInCluster 四个哨兵错误但代码中从未有函数返回它们，属于死代码。这些错误在提示词对应的错误场景中确实应该有使用位置但实现遗漏了。

过程不满意：
1. 模型收到提示词后第一步就创建了 9 项 TodoList 随后才去浏览项目目录和其他包代码。之后对 raftlog.go 进行了两轮完整重写，第一版写完后直接放弃用 Write 覆盖了文件内容，说明初版设计存在系统性缺陷需要推翻重来，这正是过早规划不做前置分析的后果。应先分析 Raft 算法的状态机模型再编码。
2. 模型在测试失败后采用修改测试断言而非修复生产代码的策略。TestAddNode 和 TestRemoveNode 失败后没有排查成员变更第二阶段的配置生效逻辑，而是放宽测试条件只验证"已启动"掩盖了生产代码缺陷。TestProposeFromFollower 偶发失败时增加了重试和等待逻辑以规避竞态而非追溯角色检查代码的正确性，属于测试向代码妥协。
3. 模型遇到偶发竞态导致 TestProposeFromFollower 失败时没有使用 go test -race 或分析根因，而是在测试中增加了 t.Skip 等规避手段。对于分布式共识这类并发密集型模块，偶发失败往往是实现正确性问题的信号，应优先追溯生产代码中是否存在锁缺失或时序假设错误而非在测试层面绕过问题。
