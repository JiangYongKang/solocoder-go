产物不满意：
1. raftlog.go 的 run 方法中 applyCommitted 是在独立 goroutine 中无锁调用的，而 propose 方法在 Leader 处理客户端请求时也会在持锁状态下调用 applyCommitted。两条协程同时对 stateMachine 进行 Apply 操作形成并发数据竞争，Go 的 race detector 可以检测到但测试未启用。提示词要求已提交的日志条目被应用到状态机，但并发应用破坏了状态机的线性一致性。根因是 applyCommitted 未受互斥锁保护，应将 Apply 操作统一在锁保护下串行执行。
2. raftlog.go 的 updateCommitIndex 方法在集群处于 JointConfig 状态时直接 return 不推进提交索引。提示词要求成员变更期间集群仍可正常处理客户端请求，但当前实现在联合共识期间所有普通日志条目的提交被阻塞，客户端请求能写入日志但永远无法被标记为已提交，实际表现为"变更期间写入暂停直到变更完成"。根因是联合共识阶段未区分配置条目和普通业务条目的提交逻辑，应在联合共识期间允许继续提交已复制到新旧配置多数节点的普通日志条目。
3. raftlog.go 的快照实现中 Snapshot 结构体的 Data 字段是 int 类型仅存储计数而非实际状态，ApplySnapshot 方法将 Data 类型转换为 stateMachine.count。这意味着快照安装后状态机只恢复了计数而丢失了所有其他状态信息，提示词要求快照包含状态机在某个索引处的完整状态但当前快照数据不完整无法真正恢复状态。应序列化完整的状态机状态而非仅传递计数器值。
4. raftlog_test.go 中 TestAddNode 和 TestRemoveNode 测试在最早版本因检查 NodeCount 失败后模型修改了断言逻辑使测试验证的是配置变更"已启动"而非"已完成"。这种放宽断言的方式掩盖了联合共识第二阶段可能存在的缺陷，如果第二阶段并未正确完成测试仍然会通过。提示词要求集群运行时动态添加或移除节点，应当验证变更完成后新节点真正加入了集群。
5. raftlog.go 中定义了 ErrNoLeader、ErrNodeExists、ErrNotInitialized、ErrNotInCluster 四个哨兵错误但代码中从未有函数返回这些错误，属于死代码。这些错误在提示词需求对应的错误场景中确实应该有对应的使用位置但实现遗漏了。

过程不满意：
1. 模型在收到提示词后第一步就创建了 9 项子任务 TodoList 随后才去浏览项目目录结构和其他包的代码。之后模型对 raftlog.go 进行了两轮完整重写，第一版写完后直接放弃并用 Write 完整覆盖了文件内容，说明初版设计存在系统性缺陷需要推翻重来，这正是过早规划不做前置分析的后果，应先分析 Raft 算法的状态机模型再编码。
2. 模型在测试失败后采用了修改测试断言而非修复生产代码的策略。TestAddNode 和 TestRemoveNode 失败后模型没有排查成员变更的第二阶段配置生效逻辑是否正确，而是直接放宽测试条件只验证变更"已启动"掩盖了可能的生产代码缺陷。TestProposeFromFollower 偶发失败时模型在测试中增加了重试和等待逻辑以规避竞态而非追溯 produce 方法中角色检查的代码是否正确。这属于测试向代码妥协。
3. 模型在遇到偶发竞态导致 TestProposeFromFollower 失败时没有使用 go test -race 或分析根因，而是在测试中增加了 t.Skip 等规避手段。对于分布式共识这类并发密集型模块出现的偶发失败往往是实现正确性问题的信号，应优先追溯生产代码中是否存在锁缺失或时序假设错误而非在测试层面绕过问题。
