产物不满意：
1. parseResponse 函数用 `_ = id` 和 `_ = flags` 丢弃响应头字段，完全未校验 RCODE 和事务 ID。当上游返回 NXDOMAIN 或 SERVFAIL 时解析器仍当作有效响应处理，丢失真实错误语义。buildQuery 生成的 ID 也未与响应 ID 对比，UDP 下可能接受它包的响应。应在 parseResponse 中保留 flags 并在调用方检查 RCODE。

2. querySingle 声明 ctx 参数但函数体完全不使用，实际独立设置超时。这导致 queryParallel 中创建的超时 context 形同虚设：首响应返回后调用 cancel，但 querySingle 不感知继续执行直到各自超时到期。高延迟下导致 goroutine 泄漏。应在 querySingle 内部 select 监听 ctx.Done() 或使用 ctx 派生的 deadline。

3. resolveRecursive 的 CNAME 追踪调用 r.resolveRecursive(cname, qtype, depth+1) 触发了从根服务器开始的完整 NS 委派链重建。当前权威服务器已确认 CNAME 指向，重建整条 NS 链是冗余的，且某级委派不可达就会导致追踪失败。应在 CNAME 分支中先尝试用当前 authoritative servers 直接查询 CNAME 目标再回退到从根重解析。

过程不满意：
1. 模型在收到提示词后的第一行动是调用 todo_write 创建了 5 项子任务计划，之后才开始阅读 go.mod、cacheinvalid.go 和 connpool.go 等已有模块以了解项目代码风格。这是标注规范中明确指出的反模式——在未分析需求文档和代码骨架的情况下直接制定计划，导致计划的粒度划分可能与实际模块边界不匹配。正确做法是先理解提示词中的功能需求，梳理包结构和现有代码的编码规范，然后再规划各子任务的执行顺序和依赖关系。

2. decodeName 函数的 DNS 域名指针偏移计算经历了至少三轮修复：初版未正确处理压缩指针跳转后的偏移量追踪，后续修复才逐步引入 jumped 标记和正确的偏移更新逻辑。每次失败后模型直接修改代码而不先阅读测试失败信息中的具体偏移值差异来精确定位，这种试错式调试导致同一函数反复修改多轮。应先运行测试获取期望值与实际输出差异，再用差异反推错误然后一次性精准修正。

3. 模型在工具调用的回复文本中使用英文表述如 "Let me also fix..."，违反纯中文输出规范。同时代码中多处无意义空白标识符赋值 `_ = id`、`_ = flags`，其中 `_ = name` 是残留代码，说明模型迭代修改后未清理，代码整洁度不足。应在完成后统一检查并移除这些无用占位符。
