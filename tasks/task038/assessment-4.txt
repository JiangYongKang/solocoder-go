产物不满意：
1. servicereg.go 的 Registry 结构体中新增的 expiryLoopStarts 字段完全是为测试目的添加的，在生产代码中无业务用途仅在 TestConcurrentStartStop 中被读取。提示词要求验证协程启动次数，模型选择在 Registry 中加入测试专用计数器，违反了"生产代码不应向测试妥协"的原则。正确做法是不改生产代码结构，通过间接方式如利用 expiryRunning 标志位注册服务实例并等待其过期回收来逆向验证后台协程正在运行。
2. Start 方法中 expiryLoopStarts 的递增在持锁阶段而 go r.expiryLoop() 启动在锁外。计数器名反映"启动决策次数"而非实际启动。虽然当前分支到 go 语句间无其他返回路径确保对应，但语义偏差构成隐式耦合。若将来重构加入分支或提前返回，计数器不再准确反映启动而测试无法捕获此错误。

过程不满意：
模型首次实现时将计数器递增语句放在 expiryLoop 协程函数体中而非 Start 方法中，运行 TestConcurrentStartStop 测试后发现测试读取计数器时协程尚未执行到递增语句导致失败，随后才将递增位置移动到 Start 的持锁阶段。这说明模型在编码前没有预判 goroutine 调度的时序特性：测试主 goroutine 在 WaitGroup 返回后立即读计数器，而 expiryLoop 中 defer 块的 wg.Done 在协程函数入口之后才注册，计数器递增如果在协程内部就必然产生竞态。模型应该先推理 Start 方法与协程体的时序关系再动手编码，而非依赖跑完测试看到失败后再反向诊断，这种"先写再修"的模式增加了不必要的往返。
