产物不满意：
1. servicereg.go 的 Registry 结构体中新增的 expiryLoopStarts 字段完全是为测试目的而添加的，该字段在生产代码中无任何业务用途，仅在 TestConcurrentStartStop 测试中被读取。提示词要求"补充对 expireLoop 协程启动次数的验证"，模型选择在 Registry 结构体中加入测试专用计数器，违反了"生产代码不应向测试妥协"的原则。若未来每次测试需要一个新的观测点，Registry 结构体就会不断膨胀引入只服务于测试的字段，破坏代码内聚性。正确做法是在不改动生产代码结构的前提下通过间接方式验证协程启动行为，例如利用已有的 expiryRunning 标志位结合注册一个服务实例并等待其被过期回收来逆向验证后台协程正在运行，而非直接在 Registry 结构体上添加仅测试使用的字段。
2. servicereg.go 的 Start 方法中 expiryLoopStarts 的递增位置在持锁阶段（第351行），而 go r.expiryLoop() 的实际启动在第354行（锁外）。计数器名为"协程启动次数"但实际反映的是"启动决策次数"。虽然当前代码从通过 expiryRunning 标志保护的分支到 go r.expiryLoop() 之间没有其他返回路径，确保了递增与实际启动的一一对应，但这种时间点上的语义偏差构成了隐式耦合。若将来 Start 方法重构时在计数器递增和 go 语句之间加入条件分支或提前返回，计数器将不再准确反映协程的实际启动情况，而依赖该字段的测试却无法捕获这一语义错误。
过程不满意：
模型首次实现时将计数器递增语句放在 expiryLoop 协程函数体中而非 Start 方法中，运行 TestConcurrentStartStop 测试后发现测试读取计数器时协程尚未执行到递增语句导致失败，随后才将递增位置移动到 Start 的持锁阶段。这说明模型在编码前没有预判 goroutine 调度的时序特性：测试主 goroutine 在 WaitGroup 返回后立即读计数器，而 expiryLoop 中 defer 块的 wg.Done 在协程函数入口之后才注册，计数器递增如果在协程内部就必然产生竞态。模型应该先推理 Start 方法与协程体的时序关系再动手编码，而非依赖跑完测试看到失败后再反向诊断，这种"先写再修"的模式增加了不必要的往返。
