产物不满意：
1. Run 方法的 defer 里不管任务返回什么错误都把状态设成 TaskStatusCompleted。比如 TestRun_MapTaskRetry_Exhausted 场景里所有 Map 重试耗尽后返回 `mapreduce: 1 map task(s) failed`，但 defer 看到状态还是 TaskStatusRunning 就直接改成 Completed，最终 Status() 返回的是 Completed 而不是 Failed。应该在 defer 里根据 Run 的返回值来设置状态，或者让各退出路径自己负责状态转换。
2. 修复 onComplete 后引入了实例不可复用的问题：第一次 Run 结束后 defer 执行了 close(mr.onComplete)，通道就永久关了。调用方再调 SetInput 设置新输入后调 Run，第二次的 defer 会对已关闭的通道再次 close 直接 panic。虽然现有测试每次创建新实例但 API 设计允许复用，应该在每次 Run 时重新创建 onComplete 通道。
3. shuffleAsync 里的 Reduce goroutine 虽然不再空转，但 finalizeAndRunReduce 只在 allMapDone 关闭后才被调用，实际 Reduce 从未在 Map 全部完成之前执行。日志显示 Reduce 启动时间跟最慢 Map 完成时间一致，说明本质还是全量 Map 完成后的批处理。提示词要求 Reduce 在 Map 没全完时就能处理已到分区数据，模型只实现了增量分组没实现增量计算，应该某个分区收齐所有 Map 结果后立即对该分区执行而非等全局信号。

过程不满意：
1. 模型第一步就建了 3 项子任务后才看代码。规范要求先分析代码再规划，模型在没理解 shuffleAsync 现有架构和 onComplete 定义背景前就定了修复计划，导致后续对状态转换的处理不周全。
2. 模型对 mapreduce_test.go 连续读了 4 次大段内容，又对 docs/mapreduce.md 连续读了 8 次。典型的高重复低效工具使用，说明缺少先用搜索或目录浏览获得概览再精确定位的意识，反复加载相同内容浪费了大量资源。
3. 模型加完 Done 通道的测试代码后直接跑 go test，编译报 `t declared and not used`（循环变量 t 覆盖了测试参数），写完代码连基本语法检查都没做。正确的习惯是写完测试后先做一次编译检查再跑测试。
