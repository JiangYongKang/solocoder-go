产物不满意：
1. csrf.go 的 RotateToken 方法存在 TOCTOU 竞态条件：ValidateToken 调用内部获取并释放读锁后返回，随后 RotateToken 才获取写锁执行删除旧 Token 和创建新 Token。两个临界区之间存在时间窗口，并发场景下另一个 goroutine 可能在同一窗口内完成同一个 session 的 Token 旋转，导致 RotateToken 中对 `c.tokens[token]` 的无条件删除删除了已经被替换掉的条目，并可能创建出在 tokens map 中存在但 sessions map 中不可达的孤儿 Token，造成内存泄漏。原因是模型未在编码前设计好锁的临界区边界，将验证和修改两个阶段割裂开。正确做法是将 ValidateToken 的验证逻辑合并到 RotateToken 的同一个写锁保护下执行，确保"验证-删除-创建"三步是原子操作。
2. csrf.go 的 GetToken 方法在检测到 Token 已过期后仅返回 ErrTokenNotFound，但未从 tokens 和 sessions 两个 map 中清除过期条目。ValidateToken 方法在同样场景下会主动调用 delete 清理过期数据，两个方法对过期 Token 的处理行为不一致。随着时间推移，过期但未被清理的 Token 会持续占用内存，直到外部显式调用 CleanExpired 才能释放。根因是 GetToken 只实现了 "判定是否存在" 的语义，遗漏了与 ValidateToken 一致的"判定时顺带清理" 的维护职责。正确做法是在 GetToken 的过期分支中添加与 ValidateToken 相同的清理逻辑。
3. csrf.go 的 Middleware 在 SynchronizerTokenMode 路径下，Token 轮换成功后仅将新 Token 设置到响应头 `w.Header().Set(c.cfg.HeaderName, newToken)`，没有同时更新 Cookie。extractToken 方法按请求头、Cookie、表单字段三级优先级提取 Token，如果客户端在上一次请求中通过 Cookie 方式传递 Token，轮换后 Cookie 中的 Token 已变为旧值且在服务端已被标记失效，客户端下次请求时若仍走 Cookie 提取路径就会因旧 Token 校验失败收到 403。而 DoubleSubmitCookieMode 路径在轮换时正确地同时更新了 Cookie 和响应头。根因是模型在写 Middleware 的轮换分支时只处理了响应头，没有对照 extractToken 的三级提取机制做完整闭环。正确做法是在 SynchronizerTokenMode 的轮换成功分支中也调用 setTokenCookie 更新 Cookie。
