产物不满意：
1. contentsec.go 的 EncodeCSS 方法中，对 `<`、`>`、`&` 三个字符的 CSS 转义使用了双反斜杠 `\\3C `、`\\3E `、`\\26 `，而正确的 CSS 十六进制转义序列应为单反斜杠 `\3C `、`\3E `、`\26 `。双反斜杠在 CSS 中被解析为"被转义的反斜杠字面量 + 文本 3C"，浏览器不会将其解释为对应字符的转义，这意味着注入到 CSS 上下文中的 `<` 和 `>` 字符实际上没有被正确编码，攻击者可以通过构造包含尖括号的 CSS 注入达成样式破坏甚至在某些旧浏览器中触发 XSS。根本原因是模型在 Go 原始字符串中错误使用了 `\\` 来表示单个反斜杠，而同一方法中对换行符 `\n`、制表符 `\t`、回车符 `\r` 的转义却正确使用了单反斜杠 `\A `、`\9 `、`\D `，内部的一致性都不满足。解决方案是将这三处 `\\3C `、`\\3E `、`\\26 ` 修正为 `\3C `、`\3E `、`\26 `，与其余转义保持统一。
2. contentsec.go 的 processTag 方法在解析 HTML 标签名时使用了 `strings.Fields` 分割标签内容后取第一个元素作为标签名，但该方法没有处理自闭合标签中斜杠紧跟在标签名后面的情况。例如输入 `<br/>` 时，标签内容为 `br/`，提取到的标签名是 `br/` 而非 `br`，而默认白名单中只注册了 `br` 而非 `br/`，导致合法的自闭合换行标签被静默丢弃，净化输出中完全丢失了换行语义。TestSanitizeSelfClosingTag 测试用例使用 `<br>` 而非 `<br/>` 作为输入，没有覆盖 XHTML 风格的自闭合写法。根本原因是未在取标签名之前先剥离尾部斜杠，应使用 `strings.TrimSuffix(tagName, "/")` 对标签名做归一化处理。
3. contentsec.go 中 DataMasker 的 Mask 方法将 patterns map 遍历后放入切片再依次应用脱敏处理，但 Go 语言中 map 的迭代顺序是不确定的。这意味着当输入内容同时匹配多个脱敏模式时，例如一个 18 位身份证号 `110101199003076578` 同时命中了 id_card 模式（18 位数字）和 bank_card 模式（16 到 19 位数字），脱敏结果会因 map 迭代顺序的不同而变化：若 id_card 先处理得到 `110101********6578`，bank_card 不再匹配，结果正确；若 bank_card 先处理得到 `1101 **** **** 6578`，id_card 不再匹配，身份证号被错误地按银行卡格式脱敏。而测试用例 TestMaskMultipleSensitiveData 中的手机号、邮箱、身份证号各不重叠，不会触发这个顺序依赖问题。根本原因是模式之间缺乏优先级机制，应按模式名称的固定顺序排序后处理，避免 map 遍历的随机性。
4. contentsec.go 的 processAttributes 方法对属性值的处理仅做了 `html.EscapeString` 转义，没有对白名单属性中允许的 URL 值（如 href、src）进行协议校验。当用户输入 `<a href="javascript:alert(1)">link</a>` 时，`a` 标签和 `href` 属性都在默认白名单中，净化后输出仍保留了 `javascript:` 伪协议，XSS 攻击载荷穿过了净化器。虽然 XSSDetector 的 javascript_protocol 过滤器可以检测到此模式，但 Sanitize 方法和 Detect 方法是独立调用的，如果调用方仅执行净化而未执行检测，攻击即可成功落地。根本原因是净化器的职责边界模糊，要么应在净化阶段主动对 URL 属性做协议白名单校验，要么应在注释或文档中明确标注该场景需要配合 XSS 检测器联合使用。
5. contentsec.go 的 EncodeJavaScript 方法对正斜杠 `/` 做了转义处理输出 `\/`，但这在 JavaScript 上下文中不是必要的：在 `<script>` 标签内 `</script>` 可以通过 `</` 序列提前闭合脚本标签，但单独的 `/` 不会造成安全风险，且 OWASP 的 ESAPI 和主流安全编码库也不建议对正斜杠做全局转义，因为这会破坏 URL 和正则表达式字面量。对 `/` 的过度转义会在编码包含路径或正则表达式的用户输入时产生意料之外的输出破坏业务功能，属于防御过度。解决方案是移除对正斜杠的转义，或仅在 `</` 序列出现时对 `/` 进行条件转义而非无条件转义。
