产物不满意：
1. bulkhead.go 的 canSubmit 方法中 idleWorkers 大于 0 时直接返回 true，绕过了队列容量限制 `len(taskQueue) < maxQueueSize`。当队列已满但有空闲 worker 时新任务仍被追加到队列中，使队列长度暂时超过配置的 maxQueueSize。在队列缩容场景下尤为突出：队列中已有 5 个任务而容量缩至 2，若此时 worker 变为空闲则 canSubmit 仍然放行。提示词要求"每个协程池有自己独立的协程数量上限和任务队列容量"，队列容量限制被绕过失去了保护意义。根因是 canSubmit 将"有空闲 worker"等同于"可以接受任务"，忽略了队列硬性容量约束。正确做法是在 len(taskQueue) >= maxQueueSize 时一律返回 false，空闲 worker 不应成为绕过队列限制的理由。

2. 提示词要求"通过信号量机制控制每个隔离舱的并发执行数量"，但当前实现是 worker 协程池模式：worker 在 for 循环中从 taskQueue 取任务执行，调用方通过 Submit 投递闭包由池内协程执行。没有提供独立的 Acquire/Release 信号量接口让调用方直接获取和释放并发槽位，调用方无法在自己的 goroutine 中执行受保护代码。这混淆了协程池（谁执行）和信号量（允许多少并发）两个不同概念，虽然 worker 数量等同于并发上限在功能上可模拟限流效果，但不符合提示词要求的"信号量机制"。根因是模型在技术选型时未区分 worker pool 和 semaphore 的语义差异，应实现带超时的信号量 Acquire 方法由调用方在任务执行前后自行调用。

3. worker 函数在取到空任务（task 为 nil）时仍执行 `b.cond.Broadcast()` 唤醒所有等待者，然后解锁再上锁。当 worker 被虚假唤醒或 cond.Broadcast 唤醒但队列已被其他 worker 抢空时，该 worker 会广播所有等待的 Submit 协程然后空转一轮回到外层循环，造成无意义的上下文切换和 CPU 浪费。根因是 worker 在 task 为 nil 的路径上包含了不必要的广播和解锁重上锁操作。正确做法是在确认 task 为 nil 时直接用 continue 回到外层循环的等待入口，不执行多余的 Broadcast 和 Unlock/Lock 操作。

4. Close 方法在 b.wg.Wait 处无超时机制，如果已提交任务函数内部死循环或永久阻塞，Close 将永远无法返回。提示词虽然没有明确要求超时关闭，但作为资源管理模块，关闭操作的可靠性是基本要求，调用方可能因此被永久挂起。根因是 Close 未考虑任务执行异常无法退出的情况。正确做法是提供带超时的 CloseWithTimeout 或接受 context.Context 的关闭方法。
