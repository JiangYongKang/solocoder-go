2. blacklist.go 的 MemoryBlacklist 中 Contains 方法对空 tokenID 的处理方式与 Add 方法不一致。Add 方法在第 59 至 62 行对空 tokenID 返回 `ErrInvalidToken` 错误，而 Contains 方法在第 73 至 76 行对空 tokenID 返回 `false, nil` 而无任何错误，视为"不存在"而非"输入无效"。这导致调用方无法区分"黑名单中确实没有这个 token"与"传入了一个空字符串"两种语义完全不同的情况，同属 Blacklist 接口的两个方法对同一非法输入给出了矛盾的行为约定。根本原因是设计时未统一 Blacklist 接口各方法的错误处理策略，Add 做了参数校验而 Contains 直接返回了温和默认值。正确做法是统一接口语义，要么两者都对空 tokenID 返回错误，要么都在方法文档中明确声明空值参数的行为预期。
3. blacklist.go 的 MemoryBlacklist 在 Close 方法执行后，再调用 Add 方法时会在第 65 至 68 行检测到 `b.closed` 为 true 后直接返回 nil 错误且不做任何存储，相当于静默丢弃了待黑名单化的 token。调用方在收到 nil 返回值时会认为黑名单操作已成功完成，实际上该 token 并未被加入黑名单，后续校验时该 token 不会被判定为已吊销，构成了隐蔽的数据丢失风险。单元测试 TestBlacklist/close 在第 714 至 725 行反而以此行为作为通过条件写死，将"静默丢弃"固化为预期行为。根本原因是 Close 后 Add 缺少明确的拒绝语义，应当在 `b.closed` 为 true 时返回一个专门标识"黑名单已关闭"的 sentinel error 而非 nil。正确做法是新增 `ErrBlacklistClosed` 错误，在 Add 方法检测到关闭状态时返回该错误，同时更新对应测试用例的预期错误。
